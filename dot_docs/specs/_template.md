# 仕様名

<!--
テンプレートから作った仕様書は、対象リポジトリのルート（`jj root`）から見た `docs/specs/` に置くことを既定とし、ユーザーが選んだ場合は GitHub Issue に置く。
各 `##` 見出し直下のHTMLコメントはAIエージェント向けの書き方と検証の指示となる。
-->

## 目的

<!--

現状の問題、適用する解、何を作るかの表明の順に書く。流し見で全体が掴める構成にする。
設計判断の一覧は目的に置かない。以下に定める項目は該当のセクションに書き、理由は判断を書いた行の下に入れ子リストで添える。

- 〜しない判断はネガティブ要件
- 値や方式を定める判断は技術的制約
-->

現状の問題を書く。

適用する解を書く。

何を作るか（この変更で達成する状態）を書く。

## 受け入れ基準

<!--
具体的な入力や操作をしたときに、期待される観測可能な結果を箇条書きで書く。
受け入れ基準に対応するテストまたは存在チェックが成功し、diff がネガティブ要件に反していないことを確認すること。
依存があるACは、見出し直下に `**Depends On**：AC-N` の独立行を置く。
-->

### AC-1：最初の完了条件

- 具体的な入力や操作を書き、期待される観測可能な結果を書く

### AC-2：依存のある完了条件

**Depends On**：AC-1

- AC-1 が完了した状態で具体的な入力や操作を書き、期待される観測可能な結果を書く

## ネガティブ要件

<!--
実装しないこと、既存挙動として残すこと、過剰実装になりやすい禁止事項を1行1事項で書く。複数の禁止事項を1行に同居させない。
やらない理由は、禁止事項を書いた行の下に入れ子リストで書く。
項目に違反する候補が出た場合は、変更に問題がないかを人間が最終判定する。
-->

- この仕様で実装しないことを書く
  - やらない理由を書く

## スコープ上限

<!--
変更量や総行数が目安を大きく超えたら、変更に問題がないかを人間が最終判定する。
-->

- **変更量の目安**：N ファイル前後
- **総行数の目安**：N 行以内

## 技術的制約

<!--
仕様に固有の技術制約を1行1事項で書く。
値を規定する場合は具体的な値を書き、理由は制約を書いた行の下に入れ子リストで書く。
-->

- 仕様に関連する技術制約を書く
  - 制約の理由を書く

## タスク一覧

<!--
進行中のタスクは `- [ ] AC-N：（進行中）タスク名` と書く。
完了したタスクは `- [x] AC-N：タスク名` と書く。
-->

- [ ] AC-1：最初の完了条件
- [ ] AC-2：依存のある完了条件
