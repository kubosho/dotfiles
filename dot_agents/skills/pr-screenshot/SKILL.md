テスト、lint、型チェックが通っても、画面の見た目は確認されていない。変更した UI を実際の画面で見て、確認した状態ごとにスクリーンショットを撮り、PR に添付する。見ていない状態を、見たかのように PR に書かない。

## 手順

1. 確認する画面と状態を決める。
   1. `jj diff` か `git diff` を読み、表示に影響する変更を探す。表示に影響する変更がなければ、そう報告して止まる。
   2. 見た目が変わる条件を洗い出す。ログイン状態、権限、データの有無、期間、feature flag、エラー、読み込み中、画面幅などが該当する。条件の組ごとに1枚、撮る状態にする。
   3. ユーザーが画面や状態を指定していれば、指定を優先する。
   4. 画像を置く節を調べる。節が Before と After の形なら、変更前の画面も撮る対象に加える。「添付」の「置く場所」を参照する。
2. 確認先を選ぶ。「確認先」を参照する。
3. アプリを起動して状態を作る。「状態の切り替え」を参照する。
4. 状態ごとにスクリーンショットを撮る。「撮影」を参照する。
5. 撮った画像を開いて見る。「画像の確認」を参照する。
6. PR に添付する。「添付」を参照する。
7. 報告する。「報告」を参照する。

## 確認先

実ページを基本にする。利用者が実際に見る画面であり、周囲のレイアウト、データ取得、認証の影響まで含めて確認できる。

Storybook は次の場合に補助として使う。

- 実ページで再現しにくい状態（エラー、空、境界値）を確認するとき
- 変更した部品がまだどのページにも置かれていないとき

実ページで確認できる状態を、Storybook の画像で代用しない。ログイン状態のようにページ側の状態で表示が変わる変更は、実ページで状態を切り替えて撮る。

## 状態の切り替え

- README、AGENTS.md、CLAUDE.md、package.json のスクリプト、シード、モックを調べ、開発環境が用意している切り替え手段を使う。モックログイン、cookie、クエリパラメータ、feature flag、固定データなどが該当する。
- ユーザーが渡していない認証情報を探して使わない。本番環境にログインしない。
- 切り替え手段が見つからない状態と、撮影に失敗した状態は、撮ったことにしない。「未確認」として理由を添え、PR と報告に書く。
- 開発サーバーが起動済みなら再利用する。自分で起動したものは、撮影が終わったら止める。

## 撮影

- 画像をファイルとして保存できる手段を使う。プロジェクトに撮影用のスクリプトがあれば優先し、なければセッションで使えるブラウザ操作の手段から、保存先のパスを指定できるものを選ぶ。画像を会話に返すだけで保存できない手段は、`gh` に渡すファイルが作れないので使わない。
- 保存先はスクラッチパッド、なければ `$TMPDIR` にする。jj はリポジトリ内のファイルを作業コピーに自動で取り込むため、リポジトリ内には保存しない。
- ファイル名は状態が分かる ASCII の名前にする（例：`campaign-logged-in.png`）。`gh` は `#` をファイル名と代替テキストの区切りに使うので、ファイル名に `#` を含めない。
- 変更が画面幅によって変わる場合は、変わる幅ごとに撮る。そうでなければ通常の幅で撮る。
- 変更前の画面を撮るときは、変更前のリビジョンを別のディレクトリに用意し、同じ状態を作って撮る。jj は `jj workspace add <パス> -r <リビジョン>`、git は `git worktree add <パス> <リビジョン>` を使う。用意するディレクトリはスクラッチパッドに作り、撮影が終わったら削除する。作業コピーは切り替えない。用意できなければ、変更前の欄は「未確認」として理由を書く。

## 画像の確認

- 撮った画像を開き、目で確認する。PR の説明、Issue、デザイン（Figma の URL があれば Figma の内容）と照らし、崩れ、はみ出し、文言の誤り、状態ごとの表示の違いを見る。問題があれば修正して撮り直す。直せない問題は報告に書く。
- 個人情報、トークン、社内限定の情報が写っていないか確認する。PR は他の人も読み、アップロードされた画像は PR の外からも参照されうる。写っている場合は、写らない状態にして撮り直す。避けられなければ添付しない。

## 添付

添付は `gh` の `--attach` を使う。形式は `'<file>#<代替テキスト>'` で、複数のファイルは `--attach` を繰り返す。代替テキストには、状態が分かる説明を書く。画像は PR の本文に入れる。

### 置く場所

次の順に探し、最初に見つかった場所を使う。

1. PR の本文にスクショ用の節がある。
2. リポジトリの PR テンプレートにスクショ用の節がある。
3. どちらにもない。本文の末尾に `## 画面確認` の節を足す。

スクショ用の節は、見出しか説明文に「スクショ」「スクリーンショット」「UI差分」「画面」「実装イメージ」「Before/After」「screenshot」などがあり、画像を置く指示が書かれている節を指す。

PR テンプレートは、`.github/pull_request_template.md`、`.github/PULL_REQUEST_TEMPLATE.md`、`docs/` 以下、リポジトリ直下、`.github/PULL_REQUEST_TEMPLATE/` 以下の順に探す。複数あるときは、本文の見出しと一致するものを使う。決められなければユーザーに聞く。

### 節への入れ方

節が見つかったら、節の指示と形に従う。

- 節の指示文（HTML コメントや説明文）はテンプレートの作者が書いたものなので、消さない。
- 表があれば、テンプレートの列を使い、セルに画像を入れる。Before と After の表なら、Before に変更前、After に変更後の画像を入れる。状態が複数あれば、状態ごとに行を足す。
- 状態が複数の軸にまたがる場合（画面幅とログイン状態など）は、行を区別するラベルの列を、表の左端に足す。軸ごとに1列とし、見出しに軸の名前（「幅」「状態」など）を使う。テンプレートの列の順序と見出しは変えない。
- 表がなければ、節の指示に合う形で、状態ごとに画像と1行の説明を並べる。
- 本文に節がなく、テンプレートの節を足す場合は、テンプレートと同じ並びで、前後の節の間に置く。

画像の参照は `![代替テキスト](./file.png)<!-- pr-screenshot -->` と書く。末尾の HTML コメントは、pr-screenshot が入れた画像を見分ける目印で、表のセルの中でも同じ書き方をする。

```md
## UI差分・実装イメージ
<!-- 必要に応じて Before/After もしくは Figma/実際の画面 のスクショを添付 -->
| Before | After |
| --- | --- |
| ![変更前のログイン済みの表示](./before-logged-in.png)<!-- pr-screenshot --> | ![変更後のログイン済みの表示](./after-logged-in.png)<!-- pr-screenshot --> |
```

画面幅とログイン状態のように軸が複数ある場合は、ラベルの列を左端に足す。

```md
| 幅 | 状態 | Before | After |
| --- | --- | --- | --- |
| 広い | ログイン済み | ![変更前の広い幅のログイン済みの表示](./before-wide-logged-in.png)<!-- pr-screenshot --> | ![変更後の広い幅のログイン済みの表示](./after-wide-logged-in.png)<!-- pr-screenshot --> |
| 狭い | ログイン済み | ![変更前の狭い幅のログイン済みの表示](./before-narrow-logged-in.png)<!-- pr-screenshot --> | ![変更後の狭い幅のログイン済みの表示](./after-narrow-logged-in.png)<!-- pr-screenshot --> |
```

どちらにも節がなければ、本文の末尾に節を足す。

```md
## 画面確認

![ログイン済みのキャンペーンページ](./campaign-logged-in.png)<!-- pr-screenshot -->
![未ログインのキャンペーンページ](./campaign-logged-out.png)<!-- pr-screenshot -->

未確認: 管理者の表示（管理者アカウントの切り替え手段がなかった）
```

本文の画像参照は、同じファイルを `--attach` に渡すと、アップロードされた画像の URL に書き換わる。参照のパスは、`--body-file` のあるディレクトリからの相対パスになる。本文ファイルは、画像と同じディレクトリに置く。

### 撮り直したときの入れ替え

入れ替える対象は、目印の付いた画像だけにする。

1. 本文全体から、目印の付いた画像の参照を、目印ごと全て削除する。表のセルは空にする。
2. 新しい画像の参照を、「節への入れ方」に従って置く。
3. 目印のない画像は消さない。作者が置いた Figma の画像などが該当する。目印のない画像があるセルに新しい画像を入れるときは、上書きせず同じセルに並べる。
4. `## 画面確認` の節は pr-screenshot が作った節なので、中身を書き直す。

### 未実施の記述

本文に「画面確認は未実施」などの記述があれば、節の内外を問わず、確認結果に合わせて直す。撮影できなかった状態は、未確認として理由とともに残す。画像を置く節と未実施の記述以外の本文は変えない。

### PR をまだ作っていない場合

ユーザーが PR の作成を求めているときだけ、`gh pr create` に `--body-file` と `--attach` を付ける。PR テンプレートがあれば、テンプレートを本文ファイルの元にして、スクショ用の節を埋める。作成を求められていなければ PR は作らず、撮影までで止めて、添付に使うコマンドを報告に含める。

### PR が作成済みの場合

1. `gh pr view <PR 番号> --json body --jq .body` で現在の本文を取得し、画像と同じディレクトリのファイルに保存する。
2. 「置く場所」で節を決め、「節への入れ方」「撮り直したときの入れ替え」「未実施の記述」に従って、本文ファイルを直す。
3. 本文ファイルを渡して更新する。

```sh
gh pr edit <PR 番号> \
  --body-file ./body.md \
  --attach './before-logged-in.png#変更前のログイン済みの表示' \
  --attach './after-logged-in.png#変更後のログイン済みの表示'
```

`--body-file` を付けずに `--attach` だけを指定すると、本文の末尾に画像が追加されるだけで、節にも入らず、古い画像も残る。必ず `--body-file` を付ける。

- 一部のアップロードが失敗すると、PR は作成または更新されたまま、`gh` が 0 以外の終了コードで終わる。PR を作り直さない。失敗したファイルを報告し、`gh pr view` で本文を取得し直して、アップロードされなかった画像の参照に手順を繰り返す。
- `--attach` が使えない場合は、`gh --version` を報告して止まる。外部の画像ホスティングへのアップロードなど、別の手段で代用しない。

## 報告

- 確認した状態と、添付先（PR の URL）、画像を置いた節（テンプレートの節か、足した `## 画面確認` か）
- 未確認の状態と理由
- 判断した点（確認先に実ページと Storybook のどちらを選んだか、どの手段で状態を切り替えたか）
- 画像の確認で見つけた問題と、直したかどうか
